# MIME Email Handling

_Enjoy a journey back to the 1980s._

This module serializes and deserializes RFC 5322 / MIME email messages. Email messages in this
format are widely supported by all email providers, including via the Gmail API.

## Data model

The `EmailMessage` type in `shared/emails/email_message.ts` is the central data structure. It holds
the envelope fields (`from`, `to`, `cc`, `bcc`, `subject`), a body with a required plain-text part
and an optional HTML part, a list of attachments, and a bag of extra headers for anything else.

All email addresses are typed as `EmailAddress` (a validated opaque string from
`shared/helpers/string/email_address.ts`). The module never deals with display names internally —
those are parsed away and the plain `addr-spec` is stored (i.e. just the address itself).

## Serialization

**`serializeEmailMessageToMimeString(message, options?)`** converts an `EmailMessage` into a raw RFC
5322 string ready to be base64url-encoded and handed to the Gmail API.

The structure it produces depends on the message content:

| Body              | Attachments | Top-level type                                     |
| ----------------- | ----------- | -------------------------------------------------- |
| Plain text only   | None        | `text/plain`                                       |
| Plain text + HTML | None        | `multipart/alternative`                            |
| Plain text only   | Yes         | `multipart/mixed`                                  |
| Plain text + HTML | Yes         | `multipart/mixed` wrapping `multipart/alternative` |

Headers always written: `Date`, `From`, `To`, `Cc` (if present), `Bcc` (if present), `Subject`,
`MIME-Version: 1.0`, `Message-ID`, `X-Alpine-Message-Id`.

Extra headers in `EmailMessage.headers` are included after the standard headers. Any header in
`reservedMimeHeaders` passed via `headers` is silently dropped — those are always set automatically.

Non-ASCII values in `Subject` and extra headers are encoded using RFC 2047 Q-encoding (see below).
Non-ASCII attachment filenames are encoded using RFC 2231 extended parameter syntax (see below).

Body text and attachment bytes are always encoded as base64 per RFC 2045 §6.8, with lines wrapped at
76 characters.

MIME boundary strings are generated by base64url-encoding a string that includes the message ID and
timestamp, making collisions with message content extremely unlikely. The serializer asserts at
runtime that the boundary does not appear in the body text, HTML, or attachment filenames.

## Deserialization

**`deserializeMimeStringToEmailMessage(raw)`** parses a raw RFC 5322 / MIME string into an
`EmailMessage`.

It handles the following top-level content types:

- `text/plain` — plain text body, no parts
- `text/html` — HTML body, no parts
- `multipart/alternative` — typically `text/plain` + `text/html`
- `multipart/mixed` — body part(s) plus attachments
- `multipart/related` ([RFC 2387](https://www.rfc-editor.org/rfc/rfc2387)) — HTML messages with
  inline resources (e.g. embedded images in signatures). Treated the same as `multipart/mixed`: the
  body is extracted from the first part and inline resources are collected as attachments.

Nested structures are handled recursively. For example, a `multipart/mixed` containing a
`multipart/alternative` body part and several attachments is correctly decomposed.

### Header parsing

- Header field continuation folding (lines beginning with whitespace) is unfolded before parsing,
  per RFC 5322 §2.2.3.
- Header values that contain RFC 2047 encoded words (e.g. `=?UTF-8?Q?caf=C3=A9?=`) are decoded
  before being stored on the `EmailMessage`.
- Duplicate headers are not accumulated — the last value for a given name wins (matching `Map.set`
  behaviour). This is intentional: in practice, the headers this module cares about (`From`,
  `Subject`, etc.) are not repeated.
- Both CRLF and bare LF line endings are accepted throughout.
- Headers in `reservedMimeHeaders` are not included in `EmailMessage.headers`. They are parsed
  separately and mapped to the typed fields on `EmailMessage`.

### Body decoding

Each body part's `Content-Transfer-Encoding` header determines how the raw bytes are decoded:

| Encoding                             | Handling                                                       |
| ------------------------------------ | -------------------------------------------------------------- |
| `base64`                             | Standard RFC 4648 base64, line breaks stripped before decoding |
| `quoted-printable`                   | RFC 2045 QP, soft line breaks removed                          |
| `7bit` / `8bit` / `binary` / missing | Passed through as raw bytes                                    |

For text parts the decoded bytes are then converted to a string using the charset from the
`Content-Type` header (defaulting to `utf-8`). Invalid charsets fall back to UTF-8 with replacement
characters.

### Attachment decoding

Attachment filenames are resolved in priority order:

1. `Content-Disposition: attachment; filename*=` — RFC 2231 extended parameter
2. `Content-Disposition: attachment; filename*0*=...; filename*1*=...` — RFC 2231 multi-segment
   parameter continuation (see below)
3. `Content-Disposition: attachment; filename=` — plain or RFC 2047-encoded
4. `Content-Type: ...; name*=` — RFC 2231 extended on Content-Type
5. `Content-Type: ...; name=` — plain or RFC 2047-encoded
6. `"attachment"` — fallback when no filename can be found

## Encoding helpers

### RFC 2047 — encoded words in headers

[RFC 2047](https://www.rfc-editor.org/rfc/rfc2047) defines a way to embed non-ASCII text in header
values using the format `=?charset?encoding?payload?=`.

**`encodeStringAsQWord(text)`** encodes a string as one or more `=?UTF-8?Q?...?=` encoded words.
ASCII strings that contain no special characters are returned unchanged. Encoded words are split to
stay within the 75-character limit per word imposed by the spec.

**`decodeEncodedWords(text)`** decodes any encoded words found in a header value. Both Q-encoding
and B-encoding (base64) are supported. Whitespace between adjacent encoded words is dropped per RFC
2047 §6.2. Unrecognised encoding tokens are left verbatim.

### RFC 2045 — quoted-printable

[RFC 2045](https://www.rfc-editor.org/rfc/rfc2045) defines quoted-printable encoding for
human-readable 7-bit-safe representation of 8-bit data.

**`encodeStringAsQuotedPrintable(text)`** encodes a string as quoted-printable with soft line breaks
so no encoded line exceeds 76 characters. Prefer base64 for any content where readability is not a
requirement.

**`decodeQuotedPrintable(encoded, charset?)`** decodes a quoted-printable string using the given
charset label (default UTF-8).

**`decodeQuotedPrintableToBytes(encoded)`** is the same but returns raw bytes (`Uint8Array`) without
charset decoding — used for binary attachments.

### RFC 2231 / RFC 5987 — non-ASCII parameter values

[RFC 2231](https://www.rfc-editor.org/rfc/rfc2231) (extended by
[RFC 5987](https://www.rfc-editor.org/rfc/rfc5987)) defines how to encode non-ASCII characters in
MIME parameter values such as
`Content-Disposition: attachment; filename*=UTF-8''r%C3%A9sum%C3%A9.pdf`.

The format is `charset'language'percent-encoded-value`. The language tag is optional and ignored
during decoding.

RFC 2231 §3 also defines multi-segment parameter continuations for long values, using numbered
suffixes: `filename*0*=UTF-8''first%20`; `filename*1*=part.txt`. Segments suffixed with `*` are
extended (percent-encoded); segments without `*` are literal strings. The charset declared on the
first extended segment applies to all subsequent extended segments.

**`decodeExtendedParameterValue(value)`** decodes a single RFC 2231 extended parameter value. If the
`charset'language'` prefix is absent the value is decoded as UTF-8.

**Encoding:** the serializer emits `filename*=UTF-8''...` (with percent-encoding via
`encodeFilenameAsRfc2231`) when an attachment filename contains non-ASCII characters, and falls back
to plain `filename="..."` for ASCII-only names.

## Address parsing

[RFC 5322](https://www.rfc-editor.org/rfc/rfc5322) defines the format of `From`, `To`, `Cc`, and
`Bcc` header values.

**`parseEmailAddressListHeader(value)`** splits an address list on commas (respecting quoted strings
and angle-addr brackets), extracts the `addr-spec` (the actual address, `example@cyberworlds.dev`)
from each entry, and validates it with `validateEmailAddress`. Display names and RFC 5322 groups
with no members (e.g. `undisclosed-recipients:;`) are dropped.

**`splitEmailAddressListHeader(value)`** and **`extractAddrSpecFromAddressListItem(segment)`** are
also exported for cases where only part of the parsing pipeline is needed.

## Known limitations

- **Semi-obscure Multiparts:** We don't support multipart messages other than
  `multipart/alternative`, `multipart/mixed`, and `multipart/related`. There's a handful of other
  types out there that perhaps we should support (like `multipart/signed` for PGP signed message
  parts).
- **Header line length:** RFC 5322 recommends wrapping header lines at 78 characters. Long `To`
  headers with many recipients can exceed this. The Gmail API accepts such headers, but some
  intermediate relay servers may fold or reject lines exceeding the 998-character hard limit.
- **Display names:** display names in `From`/`To`/`Cc` headers are parsed away during
  deserialization and are not stored on `EmailMessage`. Round-tripping a message through serialize →
  deserialize will lose display names.
- **Duplicate headers:** if the same header appears multiple times in an incoming message, only the
  last value is kept.
