# \[2022-09-05\] DynamoDB

## Context

We need a place to store and efficiently retrieve data for our application. This is an important
decision as what database you use is one of the hardest decisions to reverse in a high traffic
software system.

Considerations when picking a database:

- **Performance:** Part of our strategy for winning productivity tooling market share is having the
  highest quality product on the market. This includes having the best performance. Using the
  product should be a fluid experience and the user's train of thought should almost never be
  blocked by a loading spinner. What's a database we believe we can use to build that performs well
  out of the gate and stay fast over time?

- **Schema evolution:** As a startup we are actively evolving the product. We need to be able to
  rapidly add to and change our data schema over time as product thinking evolves.

- **Ergonomics:** How will a developer access data in code? Is it type-safe? Is there autocomplete?
  Does the API encourage best practices around performance, security, and data migration?

- **Scalability:** Is the database horizontally scalable? All the databases we are evaluating will
  likely support our scale needs for the next two to three years. However, if we are successful then
  in the next 10 years we will almost certainly need a horizontally scalable database. Migrating
  from something like single node PostgreSQL to a sharded model (or a distributed database) is
  expensive and risky.
  [Notion published their story migrating to a distributed PostgreSQL setup](https://www.notion.so/blog/sharding-postgres-at-notion).

- **Data autonomy:** This is more of a nice-to-have. The phrase comes from Jaana Dogan's (principal
  engineer who worked at GitHub, AWS, and Google) article
  [“How to peacefully grow your service”](https://rakyll.medium.com/how-to-peacefully-grow-your-service-c40c25fe097f).
  The concept is to design your data architecture so that future teams can completely redesign their
  storage layer if beneficial. This means putting all data access behind an API and disallowing
  features like `JOIN`s between multiple tables.

    Because we're building a lot of software that is very heterogenous (realtime document
    collaboration, chat, task management, video conferencing, search, calendaring) I don't believe
    there is a one-sized fits all database. I want to empower teams to make the right decision for
    their product and give them the flexibility to change that decision when new evidence arrives.

Some non-considerations that at one time I (Caleb Meredith) thought were important:

- **Universal realtime:** Our database API magically keeps track of record versions and
  automatically sends realtime updates to all connected clients. So individual products don't need
  to build their own one-off realtime solutions. This also implies a universal permissions system to
  make sure realtime isn't sending clients data they are not allowed to see.

    I built many prototypes trying to design a database API on top of a SQL database but as I spent
    more time iterating on the product I realized how different my realtime needs were across
    products that a one-sized fits all system probably wouldn't work. Document collaboration uses
    [operational transformation](https://en.wikipedia.org/wiki/Operational_transformation), chat
    messages are append only so we shouldn't really listen for realtime events anywhere but the end
    of the list, and our project management software is probably going to need pretty custom
    solutions that support realtime filtering/sorting.

    I was also exposed to the idea of data autonomy (see Jaana's linked article above) which
    conflicts with universal realtime. Overall, I think trading data autonomy for universal realtime
    is the correct decision for this product.

- **Relational database since you can dump it into a data lake:** At Airtable, we synced our
  production SQL database into Redshift for data analysis. (With sensitive fields redacted.) This
  gave anyone at the company the ability to write arbitrary SQL against our data and deliver
  business insights. You can't really do this with a document database or a key-value database. At
  one point I considered this capability a strong reason to pick a relational database.

    Recently I've learned about the idea of
    [data contracts](https://www.montecarlodata.com/blog-data-contracts-explained/). Unfortunately I
    can't find the blog post that convinced me they were a good idea. The premise is instead of
    dumping your database into a data lake, engineers carefully curate the data made available for
    analysis from their features. Establishing a contract. The schema of your relational database
    should be considered an engineering implementation detail that can change at any time, but if
    business data consumers rely on your schema for data analysis your implementation detail becomes
    an API.

## Alternatives considered

First, let me give you my categories for databases on the market. I'll explain my decision on which
database category to pick and then explain my decision on which database to pick within that
category.

In this section I will call an individual unit of data a "record". In a SQL database they call
records "rows", in DynamoDB they call records "items", and in MongoDB they call records "documents".

- **Relational:** In my mind what fundamentally differentiates a relational database from other
  databases is the ability to have
  [foreign key constraints](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-FK).
  A foreign key constraint guarantees data integrity between multiple records. That's the one
  capability which isn't present in other databases and can't be implemented at the application
  layer.

    Foreign key constraints imply you need transactions across multiple records to make an atomic
    change that doesn't invalidate the constraint. Foreign key constraints also
    [usually need to come with an index](https://softwareengineering.stackexchange.com/questions/329051/is-indexing-foreign-keys-a-good-practice)
    to speed up `JOIN`-like queries (including queries the database needs to implicitly run on
    `DELETE`s and `UPDATE`s to make sure the constraint isn't violated).

    Because foreign key constraints are fundamentally a data integrity feature (they usually do not
    influence data layout on disk) relational databases often end up having many more data integrity
    features. Like explicitly typed columns, `NOT NULL` constraints,
    [arbitrary expression `CHECK` constraints](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-CHECK-CONSTRAINTS),
    and [row level security policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

    Relational databases also come with a rich query language that lets you explore relationships
    established with foreign key constraints through SQL. (There are some less common query
    languages like [CQL](https://cassandra.apache.org/doc/latest/cassandra/cql/index.html) and
    [EdgeQL](https://www.edgedb.com/).)

    Because of its rigid constraints and structure, it can be hard to evolve the schema of a
    relational database. Relational databases typically use the types you give it to lay out records
    on disk. Meaning adding columns, removing columns, or changing the type of columns may involve
    updating every record on disk! If you are going to pick a relational database, make sure it has
    the capability to do online schema updates. You don't want downtime whenever you need to run a
    schema migration. MySQL has this tool called [gh-ost](https://github.com/github/gh-ost) and some
    PostgreSQL migrations like `CREATE INDEX` can be
    [executed concurrently](https://www.postgresql.org/docs/current/sql-createindex.html). In modern
    relational databases like CockroachDB
    [all schema changes are designed to run online](https://www.cockroachlabs.com/docs/stable/online-schema-changes.html).

    Relational databases abstract away how your data is actually stored on disk and the cost of
    executing some queries behind SQL. Not all SQL queries are created equal! Which you'll know if
    you've ever had to `EXPLAIN` a query. You have to think very carefully about what indexes you
    need, if you want to include any columns in an index, whether you should normalize any data
    (kind of defeating the purpose of foreign key constraints), and what specific `JOIN` incantation
    you need to get reasonable performance.

    The most proven relational databases MySQL and PostgreSQL are not horizontally scalable out of
    the box. You need to augment with a tool like [Vitess](https://vitess.io/) or
    [Citus](https://www.citusdata.com/) or do application-level sharding like
    [Notion described in this blog post](https://www.notion.so/blog/sharding-postgres-at-notion).
    There is a new crop of distributed relational databases including
    [CockroachDB](https://www.cockroachlabs.com/) and [YugabyteDB](https://www.yugabyte.com/) you
    could use instead.

- **Key-value:** Key-value databases like [DynamoDB](https://aws.amazon.com/dynamodb/),
  [RocksDB](https://rocksdb.org/), [Cassandra](https://cassandra.apache.org/), and
  [Redis](https://redis.io/) have many fewer features than a relational database and a much simpler
  mental model. You can only insert and retrieve data with its key. The value can be anything. Data
  is laid out on disk in key order in a [binary tree](https://en.wikipedia.org/wiki/Binary_tree).
  This makes accessing adjacent data very fast since you only need a single disk seek. Usually a key
  is made up of two parts: a partition key and a sort key. Adjacent partition keys are not adjacent
  on disk. The partition key determines, well, the partition in which the data lives. So a query to
  a key-value database is usually you say what partition key you want and the range of sort keys you
  want and the database can do a fast disk lookup to serve your data.

    Because usually you'll need more access patterns than just the data's primary key, key-value
    databases sometimes provide the ability for you to create secondary indexes.
    [DynamoDB has a secondary index feature](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/SecondaryIndexes.html).

    The consequence of using a key-value database is you have to understand well what queries you
    need to execute against your data and carefully design your schema such that data is adjacent to
    each other on disk. It can be difficult to add new query patterns and you end up writing joins
    manually in code.

    I'd argue that you need to carefully understand how your data is arranged on disk and how your
    query is running in a relational database too! SQL is a magical language that hides the
    underlying performance characteristics of your storage system in a way that key-value databases
    don't.

    Key-value databases are simple, very horizontally scalable, and have good ergonomics + data
    evolution capabilities since the value is an arbitrary object.

- **Document:** Document databases like [CouchDB](https://couchdb.apache.org/) and
  [MongoDB](https://www.mongodb.com/) have similarities with relational and key-value databases but
  feel different enough to have their own category. I won't go much more into what makes them
  different but I did pretty seriously evaluate CouchDB.

    CouchDB has a well defined
    [replication protocol](https://docs.couchdb.org/en/stable/replication/protocol.html) which,
    excitingly, can have a client-side implementation! Which is [PouchDB](https://pouchdb.com/).
    Using CouchDB means we could have a really good universal realtime story where clients sync the
    database, interact with a local database like local software, then sync changes back to the
    server. As I prototyped with CouchDB it was difficult to implement complex permission rules and
    fine-grained filtering. The “data autonomy” consideration made it clear that CouchDB would not
    be a good fit. CouchDB still could be a good fit for parts of the product! Maybe our task
    management feature uses CouchDB to achieve a feeling of fast local software.

- **Graph:** They exist but I don't understand what fundamentally makes graph databases different.
  You can build a graph on top of a relational or key-value database. I think the main difference is
  the graph query language that comes with a graph database but data layout ends up looking similar?
  I don't find query language alone a compelling reason to pick a database, I'd want to hear about
  any differentiating data layout properties to pick a graph database.

The databases I seriously considered in each of these categories and did some prototyping with were:

- Relational
    - [MySQL](https://www.mysql.com/) with [Vitess](https://vitess.io/)
    - [PostgreSQL](https://www.postgresql.org/) with application-level sharding
    - [CockroachDB](https://www.cockroachlabs.com/)
- Key-value
    - [DynamoDB](https://aws.amazon.com/dynamodb/)
- Document
    - [CouchDB](https://couchdb.apache.org/) and [PouchDB](https://pouchdb.com/)

## Decision

When I removed universal realtime as a consideration and added data autonomy as a consideration, a
key-value database became the clear choice.

- **Performance:** As a developer you are forced to think about data layout and how it influences
  performance. This is a great feature of key-value databases. You should be doing that thought with
  a relational database anyway but with a key-value database you don't get a choice.

- **Schema evolution:** The value (in our case) is a JSON object. Our custom schema framework
  supports schema evolution of JSON objects so we get pretty robust schema evolution support for
  free. It is harder to introduce new query patterns for your data and we'll likely need to build a
  data migration framework for migrations beyond what our schema framework supports. I think
  relational and key-value databases are about the same for schema evolution on balance. Relational
  databases requiring migrations that can cause downtime is pretty bad.

- **Ergonomics:** It's all JSON with a key-value database. With our custom schema framework and a
  custom SDK we get great ergonomics with type safety. For a relational database you need a
  TypeScript query builder like [Prisma](https://www.prisma.io/) to get good ergonomics. Prisma is
  maybe the best on the market but has its limitations.

- **Scalability:** Very easy to horizontally scale a key-value database. In principle and in
  practice. Horizontally scaling relational databases come with many caveats.

- **Data autonomy:** You can't do `JOIN`s against data in a key-value database. All `JOIN` like
  queries need to be carefully planned and executed at the application level. The way we structure
  our codebase is you only get access to a DynamoDB table in the file it is defined! That file
  exports functions that operate on that table and you may only access data through those functions.
  This design makes our database an implementation detail that we could swap out without too much
  work.

Then DynamoDB is the key-value database we picked. It's the only key-value database I really
evaluated, to be honest. It is managed which drastically simplifies our ops complexity and I
frequently hear the name DynamoDB talked about fondly by engineers of distributed systems I respect.

I expect [Cassandra](https://cassandra.apache.org/) is worth evaluating. A quick ergonomics point in
DynamoDB's favor is DynamoDB is all JSON whereas Cassandra has its own schema/query language.

> [2023-05-15] Note: I also expect [FoundationDB](https://www.foundationdb.org/) is worth evaluating
> as a key-value database.
>
> After more time with DynamoDB, it’s great but I worry about cost. Because of our data autonomy
> system design we can easily switch to another key-value database for individual, expensive,
> tables.

We wrote a custom API for DynamoDB instead of directly invoking the AWS SDK. This gives us great
ergonomics and the ability to add features like:

- Baked in best practices for DynamoDB table design
- Type safety and data migration with our schema framework
- Automatic request batching where applicable
- Infrastructure as code support with the [AWS CDK](https://aws.amazon.com/cdk/)
- Modern JavaScript API (e.g. async iterators for paginated requests)
- Lexicographic serialization/deserialization for attributes in keys like numbers

Here is an example of what a table definition looks like.

Items in a table have a `partitionType` and a `sortRangeType`. All data within a partition lives
next to each other on disk and is queryable in sort order.

```ts
const ForumTable = DynamoTableSchema.new({
    name: "Forum",
    partitions: {
        Channel: {
            partitionKeyAttributes: {
                channelId: DynamoKeyAttributeSchema.id<ChannelId>(),
            },
            sortRanges: {
                Attributes: {
                    sortKeyAttributes: {},
                    attributes: Schema.object({
                        spaceId: Schema.id<SpaceId>(),
                        createdTime: Schema.date,
                        name: LabelStringSchema,
                        description: MessageContentSchema.default(emptyMessageContent),
                    }),
                },
            },
        },
        Post: {
            partitionKeyAttributes: {
                postId: DynamoKeyAttributeSchema.id<PostId>(),
            },
            sortRanges: {
                Attributes: {
                    sortKeyAttributes: {},
                    attributes: Schema.object({
                        spaceId: Schema.id<SpaceId>(),
                        channelId: Schema.id<ChannelId>(),
                        createdTime: Schema.date,
                        authorId: Schema.id<AccountId>(),
                        content: PostContentSchema,
                        contentUpdatedTime: Schema.date.nullable(),
                        commentsSummary: Schema.object({
                            nextCommentIndex: Schema.integer.min(0),
                            commentCountByAuthorId: Schema.map(
                                Schema.id<AccountId>(),
                                Schema.integer.min(1),
                            ),
                        }),
                    }),
                },
                Comments: {
                    sortKeyAttributes: {
                        commentIndex: DynamoKeyAttributeSchema.integer,
                    },
                    attributes: Schema.object({
                        authorId: Schema.id<AccountId>(),
                        createdTime: Schema.date,
                        payload: MessagePayloadSchema,
                    }),
                },
            },
        },
    },
});

const ChannelPostsIndex = ForumTable.addIndex({
    name: "ChannelPosts",
    itemTypes: [{partitionType: "Post", sortRangeType: "Attributes"}],
    partitionKeyAttributes: {
        channelId: DynamoKeyAttributeSchema.id<ChannelId>(),
    },
    sortKeyAttributes: {
        createdTime: DynamoKeyAttributeSchema.date,
        postId: DynamoKeyAttributeSchema.id<PostId>(),
    },
});
```
