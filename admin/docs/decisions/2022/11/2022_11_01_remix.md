# \[2022-11-01\] Remix

## Context

To improve developer productivity, we want a web framework with common functionality for building a
website out of the box. Including:

Required features:

- **Client side routing:** Table stakes for modern web applications
- **Router with data loading:** You can improve performance and developer ergonomics by integrating
  data loading with your router
- **API routes:** Not all data can be loaded or updated through your router, API routes are an
  escape hatch
- **Route based bundle splitting:** You should only load code for the route the user is looking at

Preferable features:

- **Server side rendering:** Significant performance win for initial load
- **Nested layouts routes:** Intuitive for building complex apps and better performance when shared
  parts of the UI don't reload data/code (e.g. [Remix's layout routes][1] or [Next.js nested
  routes][2])
- **Deployable at the edge:** Running on an edge network like [Cloudflare Workers][3] is how you get
  the fastest network latency

[1]: https://remix.run/docs/en/v1/file-conventions/routes-files#layout-routes
[2]: https://beta.nextjs.org/docs/routing/fundamentals#nested-routes
[3]: https://workers.cloudflare.com/

## Decision

I (Caleb Meredith) chose [**Remix**][4] as the web framework. Remix hits all the above features. The
decision to use Remix and the decision to use [Cloudflare Workers][5] was intertwined. Remix has
great Cloudflare support which made Remix an obvious top contender for web framework.

As I adopted Remix what really stood out is its _simplicity_ (thanks to their [don't over
abstract][6] philosophy). You can pretty easily understand all the pieces. [esbuild][7] (a
straightforward, fast, build tool) makes a client and server build. The client and server runtime
code is a couple files at most and the router is the well known [React Router][8]. I would be very
comfortable forking Remix and maintaining our own version.

The [web standards][9] Remix philosophy means our code is using modern JavaScript conventions
(async/await instead of Node.js callbacks) and is portable across many environments (Cloudflare
Workers?).

## Consequences

- There's still some client side routing product requirements we have that Remix may make tricky.
  For example: opening a route in a side-sheet or showing a route preview in notifications inbox.
- [Remix was acquired by Shopify](https://shopify.engineering/remix-joins-shopify). It's unclear
  whether Shopify will continue investing in Remix or end maintenance. Remix is simple and so we are
  comfortable forking it if necessary. (We already have quite a few patches.)
- File-based routing means route files don't follow our "file names should be globally unique" code
  style.

## Alternatives considered

### Next.js

Initially I (Caleb Meredith) started building with Next.js before migrating to Remix. Having worked
in the React Org at Meta (fka Facebook) I got an early preview of React Server Components and was
excited by the vision. I used Next.js v12 then tried migrating to v13 with server components.
Next.js v12 proved fairly annoying:

- Build times with Webpack were slow
- Minimal customization of routing and data loading
- No nested layout routing meant routing was frequently not ergonomic
- Depended on Node.js, couldn't use Cloudflare Workers

I always planned to migrate to server components. Once they were available in beta and I tried
migrating, it was clear Next.js v13 wasn't ready.

- Deep Webpack integration, stuck with Webpack slow build times
- Unclear how to use custom CSS framework [vanilla extract][10]
- `"use client";` directive convention felt unfamiliar. Static tooling wasn't ready yet to make sure
  it was applied correctly everywhere
- Couldn't customize server/client serialization boundary with custom `Schema` abstraction which
  ensures cross-version compatibility and supports serializing advanced data types
- The data loading story was so nascent. The [`use()` RFC][11] had just been opened and Next.js
  appeared to be [overriding the `fetch()` global][12] with non-standard semantics. I'd have to
  write all my own data loading libraries but there was little to no documentation on how to do this
  (and everything about data loading seemed prone to change)

I had a frustrating experience trying to adopt server components. After banging my head against the
problem for a day or two I took a step back. I was using Next.js for the promise of React Server
Components but I should re-evaluate what benefit React Server Components would have for this
project.

1. React Server Components improve initial load times (similar to server-side rendering) both on
   initial load and subsequent client-side navigation (since you can server render client-side
   navigations!). However any client components needed by the new page still need to be loaded and
   render before the new page can be presented.
2. React Server Components can reduce bundle size since you can render static components exclusively
   on the server and never send their code to the client.

I care a lot about navigation time for this project, so benefit 1 was compelling. Particularly for
mobile! However, imagining the Cyberworlds UI almost _nothing_ is static.

The header has a search bar which needs to be client-side rendered and a notification bell which
needs to be client-side rendered. Feed has posts which are all interactive and have a comment
section which is also interactive. The code that will be contributing to bundle size is all the code
which powers client interactivity. You need that code even in a React Server Components world and
you need to client-render it too! So the bundle size savings from React Server Components seem
miniscule given the product and so did the navigation performance win (since so much had to be
client rendered anyway).

Previously I was very aligned with the Next.js v13 server components vision but after this
reflection I realized server components were neutral to negative performance-wise for the app I was
building. So now I was mis-aligned with the Next.js v13+ direction and I didn't want to be stuck on
v12 given I had a bad time there too (I always considered v12 temporary) so I decided to abandon
Next.js entirely.

I was also talking with Alex Dytrych at the time about migrating the document editor to [Cloudflare
Durable Objects][13]. When we started talking about Durable Objects I didn't like the idea of
complicating my stack with a new service with a different JavaScript runtime right out of the gate.
However, as I learned about Durable Objects and Workers I got more and more excited about how I
could achieve incredibly low network latency with Cloudflare.

Remix had great Cloudflare support which made it the framework I looked at next.

### Other alternatives

I very briefly considered [SvelteKit][14]. Ultimately I'm very familiar and productive with React. I
know I can build and maintain huge systems at scale with React. It didn't seem worth learning a
brand new UI framework.

[Astro][15] I didn't seriously consider but was on my radar. From a brief read of their website it
didn't seem like a fit for the client heavy app I needed to build.
