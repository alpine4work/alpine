# \[2022-11-02\] Bazel

## Context

We want a developer environment that:

- **Has fast builds:** Essential to developer productivity. This is important both locally and in
  CI. An essential part of fast builds is the ability to do remote caching. We shouldn't need to
  rerun tests/lints in CI for code that didn't change.

- **Allows programming in any language:** While we only use TypeScript for now, we may use other
  languages in the future. Like Swift on iOS.

- **Supports dependencies from any language:** We don't want to limit ourselves to using software
  dependencies from languages we work in (e.g. the npm ecosystem). For example, we'll want a custom
  FFmpeg build for image and video processing.

- **Has simple setup/maintenance:** Ideally developers only need to run one command to start their
  environment (even on a fresh machine): `dev`. This command should make sure all dependencies are
  installed and up-to-date, start local databases, start local services, and watch the file system
  for any changes so we can rebuild. Instead of making developers learn a bunch of commands (like
  `pnpm install` + `pnpm start` for JavaScript and `cargo install` + `cargo run` for Rust).

- **Is a good long term bet:** If our developer environment is founded on a tool from the JavaScript
  ecosystem, that tool is likely to go out of style very quickly. For example in 2022 when we
  started building Alpine the trendy thing to do was to just use
  [esbuild](https://esbuild.github.io/api/). In 2024 [Vite](https://vite.dev/) and to a lesser
  extent [Turborepo](https://turbo.build/) are pretty trendy. We want a good long term bet so we
  don't need to keep upgrading our developer environment.

## Decision

We picked the [Bazel](https://bazel.build/) build system as the foundation for our developer
environment. Bazel is built by Google and designed for building large scale multi-language and
multi-platform projects hosted in a monorepo. Bazel allows you to granularly define the dependencies
between all code _across languages_ in your project. And allows you to bring in third-party
dependencies hermetically.

We build on top of the [Aspect](https://www.aspect.build/) rules for JavaScript (which uses the
[pnpm](https://pnpm.io/) package manager) and don't shy away from writing our own build rules in
Skylark when necessary (Bazel's own language for defining rules based on Python).

Our `dev` command is a process manager written in Node.js that runs `bazel build` for our local
services (e.g. `bazel build //app` to build `AppService`), watches for changes, and
rebuilds/restarts services when they change.

### 2024 update

Bazel has been an excellent choice for us. It's scaled with us as the project has grown and has
helped us through a couple developer environment migrations (for example moving `AppService` from
Cloudflare Workers to AWS EC2 and upgrading the Remix build tool from esbuild to Vite).

We now write two languages in our monorepo: TypeScript and Swift. Bazel builds both of these
languages and is also responsible for building the iOS binary. (Our developer's don't need to touch
Xcode!)

We also have many dependencies defined in `WORKSPACE` from many different programming environments.
These dependencies would be incredibly cumbersome to install/maintain on a developer's machine if
not for Bazel. Being able to take on these dependencies allows us to be more ambitious while
building Alpine. Dependencies include:

- Hermetic Node.js binaries to make sure every developer uses the right version of Node.js
  regardless of their environment
- [DynamoDB local](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/DynamoDBLocal.html)
  Java `.jar`
- [OpenSearch](https://opensearch.org/) Java project
- [ElasticMQ](https://github.com/softwaremill/elasticmq) Java project as a local AWS SQS
  implementation
- Hermetic [Playwright](https://playwright.dev/) browsers (instead of installing Playwright browsers
  at a system level)
- [Open Container Initiative](https://opencontainers.org/) tools for building the containers we
  deploy to AWS
- [`all-MiniLM-L6-v2`](https://huggingface.co/Xenova/all-MiniLM-L6-v2) lightweight language model
  from Hugging Face
- [Cohere token configuration](https://huggingface.co/Cohere/Cohere-embed-english-v3.0) from Hugging
  Face for counting tokens before sending requests to the Cohere LLM API
- [`fonttools`](https://pypi.org/project/fonttools/) installed by pip for building the fonts we use
- Custom build of [FFmpeg](https://www.ffmpeg.org/) including its dependencies like `cmake`,
  `pkg-config`, `libvpx`, and `libaom`.
- Hermetic C compiler with cross-compilation support
  ([`zig cc`](https://andrewkelley.me/post/zig-cc-powerful-drop-in-replacement-gcc-clang.html))

## Consequences

Bazel requires a lot of configuration. We've spent a lot of time building and debugging custom Bazel
rules and will need to continue spending a lot of time on these rules. This is made more difficult
by the levels of indirection Bazel adds to achieve proper sandboxing. No doubt we'll have many
Alpine developers who curse Bazel's name as they try to do something that would otherwise be simple
in a standard Node.js programming environment.

The Bazel ecosystem also seems to pretty consistently have breaking changes which make upgrading a
pain. The [Aspect](https://www.aspect.build/) rules for instance just went through a pretty major
upgrade of their JS/TS rules from `aspect_rules_js` v1 to v2 which blocked our Node.js upgrade.

Finally, in order to get our environment working with Bazel it's required quite a few patches (see
`admin/patches`). For example, patching libraries like `wrangler` so they support symlinks (see
`admin/patches/wrangler@3.87.0.patch`) or patching Bazel rules like `build_bazel_rules_apple` to
make sure it uses our hermetic Python installation instead of a global Python installation (see
`admin/patches/bazel/build_bazel_rules_apple.patch`). These patches make upgrading even harder.

## Alternatives considered

[Buck](https://buck2.build/) (from Meta) is the only real Bazel alternative I know of. But it has a
significantly smaller community than Bazel so it's not really a reasonable alternative.

The main alternative would be to _not_ use Bazel and instead pick a build tool from the JavaScript
ecosystem (e.g. esbuild, Vite, Turborepo, Rollup, or Webpack). Doing this would greatly simplify our
codebase in the short term at the cost of long term complexity as the project grows (it would be
harder to start writing code in other languages, CI times would only increase as we'd no caching
across runs).
