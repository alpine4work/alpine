# \[2026-05-21\] Rynamo (formerly known as Dynamo General Realtime)

Reference: [Dynamo General Realtime](../../2023/04/2023_04_21_dynamo_general_realtime.md)

## Context

As Alpine and Cyberworlds have evolved, we've grown to realize that the realtime DynamoDb
abstraction should be the default choice for modeling data in the system. Alpine is, by nature, a
reactive application, and users expect to receive updates in real time.

We should almost always default to using the realtime abstraction.

As an example of a case that recently burned us, we built the Notion Importer without the realtime
abstraction. It seemed like a perfectly reasonable decision at the time and by the time we realized
it was the wrong choice, it was too late. In this specific example, we needed "realtime" status
updates for each import – if someone is importing 1000 documents with media, we want to continuously
inform that user of the import status.

Because we chose not to use Dynamo General Realtime, we ended up having to build a complicated
polling architecture. Had we used Dynamo General Realtime, we could have simply subscribed to the
status updates as they were written to the database.

Okay, so we decided that we should bias toward the realtime abstraction, now what?

Well, one of our software design principles at Alpine is that we should give "scary" / "ugly" names
to things that other devs should think twice about using and the `DynamoGeneralRealtime` moniker is
pretty ugly. By itself, it's not so bad, but the problem starts to conflate with the naming of
things like `createDynamoGeneralRealtimeQuerySchema` or `useDynamoGeneralRealtimeItem` or
`getDynamoGeneralRealtimeEventTransaction` etc.

So we sought to create a new naming convention for the Dynamo General Realtime abstraction that
would be more developer-friendly.

## Decision

First, we are making it official: **new data models should default to the realtime abstraction**.
Reach for non-realtime storage only when there is a concrete reason the realtime abstraction won't
work, and document that reason.

Second, we are renaming the abstraction. And thus, `Rynamo` was born — a portmanteau of "Realtime"
and "Dynamo". It is short, pronounceable, and composes cleanly into identifiers like
`createRynamoQuerySchema` and `useRynamoItem`.

We also made the following related changes:

1. Renamed `broadcastEventTransaction` to `broadcastEvents`.
2. Renamed `eventTransaction` to `events`.
3. Moved `server/dynamo/core/rynamo` to `server/rynamo` so that it is a top-level server directory.
   The abstraction is no longer a sub-piece of our Dynamo tooling — it is a first-class building
   block for modeling data in Alpine, and its location in the tree should reflect that.
