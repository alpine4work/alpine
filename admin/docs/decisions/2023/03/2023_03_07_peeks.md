# \[2023-03-07\] Peeks

## Context

Peeks are a product solution to the user problem of having hundreds of unnecessary tabs and windows
open at any time. The product hypothesis is new browser tabs and windows are too heavy and distract
from the user's core task when they are trying to quickly retrieve some information. Peeks keep the
user in the context of their current task while providing an independent navigation context.

We only allow one peek to be open at a time. If a peek is open and a user clicks a link that would
open another peek, we stack the new peek on top of the first. Visually it looks like a stack of
paper. Peeks that are not on top of the stack may be unrendered for performance. So we don't need to
maintain realtime connections and updates for them.

So to build this we need the capability to have our own mini-navigation context within a browser
tab. This context should be able to:

- Bundle splitting across peek routes
- Navigate across links within the context
- Expand to fullscreen if the user wants to focus the content
- Be mounted/unmounted easily
- Maintain navigation state across page reloads (just like a real browser tab)
- Have access to root React contexts so data/interactions can be shared across peeks and the main
  app

## Decision

Use [Remix](https://remix.run/) internal navigation primitives to create a new navigation context
embedded within the broader React app.

We have “peek routes” under `/s/$spaceId/peek/*` that correspond to identical routes in
`/s/$spaceId/*`. So to expand a peek route we drop `/peek` from the URL. This gives us bundle
splitting and server data loading for free. If Remix adds more server-client features (like
[`defer()`](https://github.com/remix-run/remix/releases/tag/remix%401.11.0) or React Server
Components) we can leverage them for peeks since peeks are integrated with Remix routing. We can
also easily use the same code across the peek route and main route with `export * from "..."`.

Remix is neatly abstracted so that each layer has clean boundaries and we can swap out different
parts for our use case. Remix is built on top of [React Router](https://reactrouter.com). React
Router is in turn built on the [history](https://www.npmjs.com/package/history) library. Importantly
the history library has a browser history implementation (that updates the browser URL) and a
_memory_ history implementation (that maintains navigation state in-memory). So if we can render a
nested copy of React Router + Remix with a memory instance of the history library we have our
feature.

Remix v1.7.5 has this layer between the history library and React Router called
“[transition manager](https://github.com/remix-run/remix/blob/32337757eba981e5d9705e40ad084d9d5c2d2bf2/packages/remix-react/components.tsx#L117-L127)”
which handles data loading when navigating to routes. This is a private implementation detail of
Remix so may change without notice at any time. So we create a new transition manager for our memory
history instance and pass the relevant location state to React Router.

To maintain navigation state across reloads we can put the memory history state in `sessionStorage`
(keyed by the history library’s `location.key`).

## Consequences

Building peeks this way does require careful knowledge of Remix and React Router internals. We also
need to patch the libraries in certain cases to get the behavior we want for nested routers or to
get access to certain data.

For example, we need to import transition manager from `@remix-run/react/dist/esm/transition`.
Importing from a `dist` folder should scare you. This is at Remix v1.7.5, the latest version at the
time of writing is Remix v1.14.1 and in this version transition manager has been removed completely
and the concept entirely deprecated! (See the new
[`useTransition()` implementation](https://github.com/remix-run/remix/blob/0bcb4a304dd2f08f6032c3bf0c3aa7eb5b976901/packages/remix-react/components.tsx#L1173-L1198).)
Remix moved a lot of its
[data loading responsibilities into React Router](https://remix.run/blog/remixing-react-router).

This will make upgrading Remix hard. We’re already behind! Over time we should advocate for the
Remix + React Router project officially supporting primitives for this use case. It shouldn’t be too
hard. The core thing we need from Remix is the ability to have a nested memory router within a
browser router. The Remix project’s move to put data loading into React Router should make this
easier for us since the abstraction boundaries we depend on are cleaner.

## Alternatives considered

- **Rendering peeks in an iframe:** Have a similar routing convention where `/s/$spaceId/peek/*`
  corresponds to the same `/s/$spaceId/*` route but render the `/s/$spaceId/peek/*` route in an
  iframe. This has pretty severe UX and performance drawbacks. From a UX perspective we couldn’t
  access React context from the root of the app which would stop us from opening modals or toasts at
  the app level. From a performance perspective we couldn’t share in-memory caches. For example the
  route module cache. Every navigation would need to fetch and evaluate the route’s JavaScript code
  fresh.

- **Building our own router:** We could have an `abstract class PeekBase` with a function to get
  data (Remix’s `loader`) and render a component (Remix’s default React component export). Then you
  construct subclasses like `new DocumentPeek()` and open those. The developer would have to
  remember to manually bundle split with `import()`. All the peek subclasses would effectively serve
  as our own route manifest which Remix already has. The features of this abstract peek class just
  felt more and more like what Remix already provided. Deep integration with Remix also gives us a
  more powerful client-server connection which can evolve with features like server components in
  the future.
