# \[2023-04-21\] Rynamo (formerly known as DynamoDB General Realtime)

## Context

We are building a collaborative application. This means we need to show users changes from their
coworkers immediately as they happen. Realtime systems are notoriously difficult to build. There are
a host of challenges (described below) to overcome. So far, for every new product feature we’ve
designed a new realtime system from (almost) scratch. Documents, chat, and forum posts all have
their own realtime systems. There are some shared components like our WebSocket abstraction (see
`server/cloudflare/web_socket_server.ts`) or messaging protocol (see
`shared/messaging/messaging_realtime_protocol.ts`) but the core is reimplemented every time. This
increases the cost to build new features and leaves room for bugs (will every implementation have
correct backfill logic?).

We want a general purpose realtime abstraction we can use for a wide variety of different product
applications. That way, new realtime features can be guaranteed to be built fast and built correct.
We use DynamoDB as our data store so realtime should be built on top of that.

This abstraction does not need to support _every_ realtime use case in our app. Document
collaboration will likely always need a custom solution to achieve best performance. But the
abstraction should solve 80% of common realtime use cases.

Challenges to consider when designing our realtime abstraction:

- **Event production:** Every update that causes data loaded by the client to update should produce
  an event to be delivered by the client. If multiple updates happen in a DynamoDB transaction then
  all those events should be delivered and applied as a transaction. We should not allow updates to
  the DynamoDB table that we can not produce a realtime event for.

- **Event consumption:** When the client receives a realtime event it should be able to incorporate
  the event into its local state so the client has the same view as data on the server.

- **Event ordering:** In a distributed system, race conditions abound. Even if updates are strictly
  ordered by a centralized service (in our case, the `updateLockVersion` attribute in DynamoDB
  items) the realtime events generated by those updates may not arrive to clients in the right order
  if the updates were made by different processes. Our abstraction needs to either guarantee events
  are delivered in the right order or guarantee that the client will process events in the correct
  order regardless of the order they were delivered. (The latter is usually easier and less resource
  intensive since you don’t need a stateful backend service maintaining message order.)

- **Event backfill:** A page loads data from the server and later connects to realtime on the
  client. It needs to backfill events that occurred during the page load while not connected to
  realtime to guarantee we present the right data to users. Similarly if a client loses its realtime
  connection temporarily (maybe the user moves through a tunnel) when it reconnects it needs to
  backfill realtime events it missed. The abstraction should have a correct realtime event backfill
  implementation.

Our abstraction does _NOT_ have to handle:

- **Strong consistency:** This abstraction can use an eventually consistent model. This means if
  item A is updated then item B is updated later, we are ok if the client shows the new version of
  item B alongside the old version of item A as long as item A is eventually updated to the correct
  version on the client. DynamoDB itself only enforces that
  [operations on individual items are serializable](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html),
  updates across items are not serializable. Unless the updates are in a transaction, our realtime
  abstraction must respect DynamoDB transactions. Similarly, it is ok if a client skips an update.
  Say item C is updated twice, once to version n+1 then again to version n+2, then we deliver the
  n+2 update first. In this case the client may incorporate the version n+2 update immediately so
  when the version n+1 update is delivered the client must discard it.

- **Event delivery:** The abstraction user may still be responsible for delivering realtime events.
  Our DynamoDB abstractions currently have no knowledge of authorization permission rules or our
  Cloudflare Durable Objects WebSocket setup. So you’ll still need to wire up event delivery to the
  client and make sure the client is authorized to read a given event stream. This should be simple
  using our WebSocket abstraction (see `server/cloudflare/web_socket_server.ts`).

## Decision

We built the DynamoDB general realtime abstraction to meet the need for a general purpose realtime
system. It has some limitations so it’s not appropriate for every realtime workload but should be
appropriate for 80% of workloads.

You must define a table as a general realtime table when you create it. Instead of using
`DynamoTableSchema.new()` you use `RynamoTableSchema.new()`. Under the hood `RynamoTableSchema` is
creating a `DynamoTableSchema` so table schema definition is identical except we add the following
properties to your schema:

- `models`: For every item in your table, you must provide a model builder function. Models are what
  we send to the client. We don’t send the raw item stored in the table. Your model builder function
  can load related data like the name of an account.

    The model builder function should ignore the current actor! If a user updates an item then we
    will build a model that will be sent in a realtime event to all other connected users. This
    model should contain no personalization to the user who updated it since other users would see
    that personalization.

- `modelSchema`: A union schema for all models returned by model builder functions in `models`. Used
  to serialize/deserialize realtime events.

- `broadcastEventTransaction`: The abstraction does not handle event delivery for you. You are
  responsible for delivering realtime events to clients. This function is called whenever a new
  realtime event transaction is produced.

### How it works

Every item is required to have a monotonically increasing `updateLockVersion`. This allows clients
to serialize updates to an item. The item with the latest version always wins. This means
`RynamoTableSchema` does not support the `createOrReplaceItem()` and `replaceItem()` methods as they
do not monotonically increase the item’s `updateLockVersion`.

(At the time of writing `RynamoTableSchema` also doesn’t support `deleteItem()`, though it should
eventually. To implement `deleteItem()` we will need to leave “gravestone” items. If you recreate an
item that has been deleted it should have an `updateLockVersion` that’s +2 of the item version when
it was deleted. The deletion itself updates the version +1 then recreating the item updates the
version +1 again. This way client’s can correctly order deletion realtime events.)

`RynamoTableSchema` does support `createItem()`, `updateItem()`, and `directlyUpdateItem()` as well
as the transaction versions of these methods. When one of these methods are called,
`RynamoTableSchema` produces a realtime event (using the provided model builder function for the
item) that is then delivered to clients.

For reading data `RynamoTableSchema` has `getRealtimeItem()` and `realtimeQuery()`.
`getRealtimeItem()` returns the model for a single item and you use `useRynamoItem()` on the client
to keep the item up-to-date in realtime. `realtimeQuery()` returns a range of items from the table
(or from an index on the table) and you use the `RynamoQuery` class (or `RynamoIndexQuery` class for
index queries) on the client to keep the range of items up-to-date in realtime.

Table queries and index queries differ in that for table queries items are sorted by their key
whereas for index queries items are sorted by a cursor specific to that index.

(At the time of writing we’ve only implemented `realtimeQuery()` for indexes since that’s all our
first use-case needed. But it should be simple to follow by example to implement `realtimeQuery()`
for the base table.)

#### Item realtime representation

`getRealtimeItem()` and `realtimeQuery()` do not directly return items from DynamoDB! Instead they
return a result object that’s safe for sharing with clients. The result also contains information
necessary for the client to interpret realtime events. This includes:

- The item’s model (using the schema’s model builder functions)
- The item’s key
- The item’s version
- A cursor for the item in an index (index `realtimeQuery()` only)
- Read time for a query (`realtimeQuery()` only)

Item keys and cursors are opaque base64 encoded binary data. They are lexicographically sortable so
if `cursor1 < cursor2` that means the item with `cursor1` appears before `cursor2` in a query.

The item key includes all the data in an item’s DynamoDB primary key. The item cursor includes the
data for the sort key of an item’s DynamoDB index key (the partition key of a DynamoDB index key
does not participate in sorting so is not included). Both DynamoDB primary keys and index keys are
defined in our abstraction with the `DynamoKeyAttributeSchema` class which includes a binary
encoding for most field types.

(At the time of writing we don’t have a binary encoding for `DynamoKeyAttributeSchema` strings since
order-preserving binary encoding for strings can be tricky.)

When base64 encoding, we use a URL-safe base64 dictionary that preserves order. Instead of the
standard base64 dictionary (see `Rfc4648UrlWithOrderPreservation` in
`shared/helpers/binary/base64.ts`). This way, the item key/cursor string order is the same as the
binary order. And the binary order is the same as the underlying value order.

#### Client event backfill

When the client connects to realtime, it needs to backfill realtime events it missed.

- To backfill `getRealtimeItem()` we re-read the item with DynamoDB’s strong consistency mode when
  we connect to realtime. If the item version is greater than what’s on the client we incorporate
  the new item.

- To backfill `realtimeQuery()` we read from an event log starting at the read time property
  included in the query result. So if we read a query on the server and it took 10 seconds to
  connect to realtime on the client, we read the last 10 seconds worth of events from our event log.
  Similarly, if the user’s device goes offline for 5 minutes then when they reconnect we will read
  the last 5 minutes of events from our log and incorporate them on the client.

    This means we need storage for an event log in our realtime table. Writes are therefore more
    expensive when using our realtime table abstraction. We give items in our event log an ~1 week
    expiration time so they don’t contribute to storage costs.

    In our event log, we don’t store intermediate item values! That means if we query our log and
    see 5 updates to an item, we will only be able to read the latest item value. Not the item at
    version n-2. This reduces our storage costs but means clients can not depend on seeing every
    update to an item.

## Consequences

Our general realtime abstraction works well when:

1.  Every individual item in your table needs to be updated in realtime
2.  You don’t have multiple items forming larger “entities”
3.  Clients don’t need to see _every_ update, it’s ok if some updates are skipped
4.  Clients can have an eventually consistent view of items in the table, it’s ok if some items are
    temporarily at inconsistent versions

Documents would _not_ work with our general realtime abstraction. A single document is composed of
many individual step items. These step items are immutable. They do not change after creation. It’s
also critical that you receive every update to a document so clients can rebase their local updates
in collaborative editing contexts (learn more about the
[operational transformation](https://en.wikipedia.org/wiki/Operational_transformation) system
documents use).

Chat messaging _may_ work with our general realtime abstraction but was built before the abstraction
existed. Even though it could work with the general realtime abstraction, there are benefits to
building custom realtime for chat. It’s more harmful to users in a chat context to see messages
jumping in at weird positions as the UI settles to an eventually consistent idle state. We also get
some efficiencies by leveraging the fact that we know creating items in a chat will always be append
only.

## Alternatives considered

The general realtime abstraction was built, initially, for the notifications use-case. I (@calebmer)
could have built a custom realtime implementation for notifications like I already had for documents
and chat. But I have had this idea for a general purpose realtime system on DynamoDB for a while and
know I’ll have other features come up that could use it, so decided to invest a little more time
into building an abstraction instead of another one-off realtime system. Hopefully this pays off in
time savings when building future features.
